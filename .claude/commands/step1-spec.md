description: Step 1 — docs/spec.md を対話形式で作成する
---

docs/spec.md を対話形式で作成する。次の手順で進めること。

手順
1. リポジトリ内の既存資料 (CLAUDE.md・README.md・`inception/`・過去のメモ) をすべて読む。
2. spec.md に必要な情報のうち、資料から読み取れない・曖昧なものを
   洗い出して質問する。下記6カテゴリを漏れなくカバーする。
   カテゴリごとに区切って質問してよい。
3. 回答を反映する。答えられない項目は推測で埋めず
   「未確定（いつ・誰が決めるか）」として記録する。
4. 全カテゴリが埋まる、または残りが未確定として確定したら
   docs/spec.md を生成し、未確定事項の一覧を再掲する。

質問で必ずカバーするカテゴリ
A. 案件タイプ — UI案件 / 非UI案件（混在は UI案件に倒す）
B. 機能要件 — 各要件に優先度と、テスト可能な受入基準
C. スコープ — やること / やらないこと（特に「やらないこと」。将来構想の
   VIX・為替・金利・債券入札・個人消費のどこまでを初版に含めるか）
D. 非機能要件 — 必ず数値で（「速い」ではなく「p95 < 300ms」）。
   データ更新頻度・保持期間・欠損時の許容挙動も数値・条件で書く
E. 制約・前提 — 完全無料スタック / データソース API とその利用規約・レート制限 /
   Supabase・GitHub Actions の無料枠 / 既存連携
F. データ仕様 — 各指標の定義と出所（フォワード EPS か実績 EPS か、期間、
   算出元、更新タイミング、ライセンス・再配布可否）

不明点を推測で埋めることは禁止。特に金融指標の定義は一次情報で裏取りする。

spec.md の構成
- 冒頭: 案件タイプ
- 機能要件（優先度・受入基準つき）/ スコープ（やる・やらない）
- 非機能要件（数値）/ 制約・前提 / データ仕様（指標ごとの定義・出所）
- 未確定事項（項目ごとに「いつ・誰が決めるか」）
