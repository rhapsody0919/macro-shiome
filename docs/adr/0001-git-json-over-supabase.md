# 0001. データストアに Supabase ではなく Git 内 JSON を採用

- ステータス: 採用
- 日付: 2026-08-16
- 関連: SDD Step 2 (Issue 未起票)

## 背景

当初要件では「Supabase へ UPSERT」を前提としていた。Step 2 で無料枠を公式ドキュメントで確認した
ところ、本アプリの利用形態と噛み合わない制約が見つかったため、代替案を含めて再検討した。

本アプリのデータ特性:
- 更新は**週 1 回**のみ (GitHub Actions の週次バッチ)
- 閲覧アクセスも多くない (個人利用が中心)
- データ量は週次 12 指標 × 52 週 × 10 年 ≒ 6,200 行 + 日次系列 ≒ 25,000 行 = **約 3 万件**
- 画面からの書き込みが無い (読み取り専用ダッシュボード)

## 検討した選択肢

| 評価軸 | 案 A: Supabase | 案 B: Git 内 JSON | 案 C: Cloudflare D1 |
| --- | --- | --- | --- |
| 無料枠 | 500MB / egress 5GB | リポジトリ容量のみ | 5GB / 500 万行読取per日 |
| **停止リスク** | **1 週間の非活動で自動停止** | 無し | 無し |
| クライアントの秘密情報 | anon key が露出 (RLS 前提) | 不要 | Workers 経由なら不要 |
| クエリ | SQL | 全件読み込み + クライアント処理 | SQL |
| データ変更履歴 | 別途設計が必要 | git が履歴になる | 別途設計が必要 |
| 運用負荷 | RLS 設計・キー管理・停止監視 | ほぼ無し | Workers の実装 |

各案の不適合点:

- **案 A**: [公式](https://supabase.com/pricing)に "Free projects are paused after 1 week of
  inactivity." と明記されている。**週次更新かつ低アクセスの本アプリは、この条件を踏みやすい。**
  停止すると画面が動かなくなり、復旧に手動操作が要る。また public リポで anon key を扱うため
  RLS の設計ミスが即座に事故になる
- **案 B**: データ量が増えると破綻する。SQL クエリができない。同時書き込みができない
- **案 C**: v1 に SQL が必要な場面が無く、Workers の実装コストに見合わない。過剰な選択

## 決定

**案 B (Git 内 JSON) を採用する。**

- 取得結果を `data/observations/{indicatorId}.json` としてリポジトリに commit
- push が Cloudflare Pages のビルドをトリガし、静的サイトとして配信

## 理由

1. **停止リスクが無い**。案 A の "1 week of inactivity" は本アプリの利用形態と直接衝突する
2. **データ量が DB を必要としない規模**。約 3 万件 = JSON で数 MB、gzip 後は数百 KB
3. **クライアントに秘密情報が一切出ない**。静的 JSON を読むだけなので anon key すら不要。
   public リポである本プロジェクトの制約と噛み合う
4. **git が履歴になる**。「いつ・どの値が・どう変わったか」が commit として自動的に残る。
   予想 EPS の改定を追う本アプリでは、データ自体の変更履歴に価値がある

## 影響・トレードオフ

- **失うもの**: SQL クエリ、同時書き込み、大容量への拡張性
- **クライアント側の負担**: 期間フィルターは全件読み込み後にクライアントで処理する。
  数千点なので実用上の問題は出ない。画面用ビュー (`data/views/*.json`) をビルド時に生成して緩和する
- **commit の増加**: 週 1 回のデータ commit で年 52 件。リポジトリ肥大の懸念は当面無い
- **再検討の条件**: 指標が増えてデータが **50MB を超える**、または**画面からの書き込みが必要に
  なった**時点で案 A / 案 C を再評価する
